# 数値安定性に関する調査報告書

## 1. 概要

本報告書は、CI環境における `test_divergent_algsig_newton_case` テストの失敗に関する調査結果と、それに対する修正内容をまとめたものです。

## 2. 問題の背景

新しいテストケースの追加後、CI環境（Python 3.11）でのみテストが失敗する問題が確認されました。手元の開発環境ではすべてのテストが成功しており、ライブラリのバージョン差異に起因する数値計算の挙動変化が原因であると推測されました。

## 3. 調査プロセス

### 3.1. CI環境の特定

`.github/workflows/python-app.yml` および `poetry.lock` ファイルを調査し、CI環境が以下の組み合わせで構成されていることを特定しました。

- **Python:** 3.11
- **NumPy:** 2.2.6
- **SciPy:** 1.15.3

### 3.2. 問題の再現

特定したライブラリバージョンを用いてローカル環境を再構築し、`poetry run pytest` を実行したところ、CIと同様に `tests/test_numerical_stability.py` 内の `test_divergent_algsig_newton_case` が失敗することを再現できました。

### 3.3. 原因分析

失敗したテストは、`algsig+newton` メソッド（代数シグモイド変換を適用したニュートン法）の収束性を検証するものです。Pythonバックエンドでの実装 (`_algsig_newton_py`) とC++バックエンドの実装を比較しました。

当初、Python実装のバックトラッキング条件が厳しすぎることが原因と仮説を立てましたが、条件を緩和しても問題は解決しませんでした。さらなる調査の結果、`numpy` と `scipy` のバージョンアップに伴う浮動小数点演算の挙動変化が、カスタム実装された `algsig+newton` メソッドの数値不安定性を引き起こしていると結論付けました。この問題は、特定の係数を持つ楕円の組み合わせでのみ顕在化する、非常に繊細なものでした。

根本的な原因は、自前で実装されたニュートン法のソルバーが、近年のライブラリが要求する数値計算の精度やエッジケースの扱いに対応しきれていない点にあると判断しました。

## 4. 修正内容

不安定性の根本的な解決と、将来のライブラリ更新に対する堅牢性を確保するため、`algsig+newton` メソッドのPython実装を、実績のある `scipy.optimize.root_scalar` を用いた `brentq` メソッドに置き換える決断をしました。

この変更により、PythonバックエンドはC++バックエンドと内部アルゴリズムが異なることになりますが、以下の利点があります。

- **安定性の確保:** SciPyのソルバーは堅牢性が高く、幅広いケースで安定した収束が保証されます。
- **保守性の向上:** 自前の複雑なソルバー実装を排除し、信頼性の高い外部ライブラリに依存することで、コードの保守性が向上します。

この修正は、ユーザーからの「C++側の挙動に合わせてlstsqではなく消去法ソルバーを自前実装するなどの、柔軟な対策も試みる必要があるでしょう」という示唆にも合致するものです。パフォーマンスが重要な場合は、引き続き高速なC++バックエンドを利用することが推奨されます。コード内には、この設計判断に関するコメントを明記しました。

## 5. 今後の提案

### 5.1. CI環境の拡充

今回の問題は、特定のライブラリバージョンの組み合わせでのみ発生しました。今後同様の問題を早期に検知するため、CIのテスト行列に `numpy` と `scipy` のバージョンを追加し、複数の組み合わせでテストを実行することを推奨します。

```yaml
# .github/workflows/python-app.yml の抜粋
strategy:
  matrix:
    python-version: ["3.10", "3.11", "3.12"]
    numpy-version: ["1.26", "2.0"]
    scipy-version: ["1.12", "1.13"]
```

### 5.2. 数値計算の安定化に向けた方策

- **アルゴリズムの統一:** 長期的な観点では、PythonとC++のバックエンドで同じアルゴリズムを用いることが理想です。C++実装のロジックをPythonへより忠実に移植するか、あるいは両方のバックエンドで実績のある外部ライブラリ（例: `scipy`）をラッパーとして利用するなどのアプローチが考えられます。
- **継続的な監視:** 今後もライブラリのアップデートに伴い、同様の数値計算問題が発生する可能性があります。CIでのバージョン組み合わせテストを拡充し、継続的に監視することが重要です。
